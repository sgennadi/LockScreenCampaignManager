# Background Deferred Repair — инструкция (0.4.0-preview.6)

## Зачем нужен

Раньше отложенный Repair повторялся только при открытом GPO Operations. Фоновый режим позволяет закрыть менеджер и продолжить **ранее одобренные** безопасные RPC-повторы, а также проверку Client Health.

Это НЕ служба Windows: используется отдельная задача обычного Windows Task Scheduler, запускающая тот же переносимый EXE с параметром \`--background-repair-once\`.

## Включение

1. Запусти опубликованный \`LockScreenCampaignManager.exe\` в Windows под текущей доменной учётной записью администратора с правами на нужные клиентские ПК.
2. Подключись к домену. Для фонового режима выбери **Current Windows account** (не **Other domain account**).
3. В **GPO Operations → Client Health / Live** установи отдельную доступную SMB-шару отчётов; не SYSVOL и не NETLOGON.
4. Открой **Отложенный Repair** и включи **Фоновая обработка (Task Scheduler...)**. Прочти подтверждение и согласись с установкой задачи.
5. Отныне **НОВЫЕ** Repair Selected / Push Now → Repair получают разрешение фонового обслуживания после обычного Preview и ввода точного GUID GPO.
6. Можешь закрыть окно GPO Operations или весь менеджер. Задача Windows проверяет очередь раз в 2 минуты, **пока этот Windows-пользователь вошёл в систему**. ПК, включившиеся позже, будут восстановлены только в пределах ранее разрешённой области.

Важно: при **Sign out/Log off**, когда интерактивная сессия завершена, задача **не** продолжает выполнять RPC: пароль пользователя специально не сохраняется. Windows Lock / заблокированный экран с сохранённой сессией этому не мешает. Для круглосуточного исполнения без входа администратора потребуется отдельная служба под ограниченной gMSA — в этой версии её нет.

## Что происходит при обработке

- Менеджер или worker читают очередь из профиля администратора: \`%LOCALAPPDATA%\LockScreenCampaignManager\DeferredRepair\queue.json\`.
- Фоновая задача читает только записи с явным разрешением и совпадающим SID Windows-пользователя.
- Вначале проверяется отчёт клиента; если агент восстановился сам, повторный RPC пропускается.
- Если статус \`Queued\` ещё требует восстановления, перед новым RPC перепроверяются AD OU, Security Group, GPO, CampaignID и свежий хеш Preview.
- До RPC на диск записывается \`Attempting\`. Обрыв, неизвестный статус или аварийное закрытие не запускают повторную команду.
- Максимум один RPC-повтор и до 20 SMB-проверок за цикл. Лимиты предыдущего механизма не меняются: до 20 попыток и не более 14 дней после исходного одобрения.
- \`AwaitingHealth\`, \`AwaitingTask\` и \`Attempting\` ждут свежий правильный отчёт. После двух часов без подтверждения запись требует внимания администратора.
- Прежние записи, созданные до включения фонового режима, автоматически **не** получают новые полномочия. Если первоначальная команда была запущена с альтернативными данными, она остаётся ручной.

Если администратор повторно подтверждает новый Repair для того же ПК, старое разрешение фонового `Queued` атомарно отзывается до запуска команды. Фоновая задача проверяет разрешение повторно непосредственно перед RPC, поэтому параллельный старый повтор не выполняется. Записи `Attempting` / `AwaitingHealth` / `AwaitingTask` нельзя перезапускать, пока администратор не разберёт предыдущую попытку.

## Где посмотреть / выключить

Вкладка **Отложенный Repair** показывает очередь и время последнего цикла. Windows Task Scheduler содержит задачу вида \`LSCM-BackgroundRepair-S-1-5-...\`; она видима администратору, использует **Run only when user is logged on** и запускает текущий EXE из его фиксированного пути.

Чтобы выключить, сними галочку **Фоновая обработка**. Сначала отключается локальное разрешение, затем удаляется задача Windows. Сами заявки из очереди не удаляются. При смене пути EXE выключи и включи фон заново (иначе запланированная задача может ссылаться на отсутствующий файл).

Доступ к SMB/NTFS-папке отчётов, GPO/SYSVOL и RPC должен работать **от текущего Windows-пользователя**. Никакие доменные пароли, LAPS или BitLocker-ключи не записываются в настройки фонового режима.

## Проверки перед эксплуатацией

Протестируй на отдельной OU минимум один выключенный компьютер, один доступный и один с закрытым RPC. Проверь восстановление после повторного включения, закрытия GUI, блокировки сеанса, выхода пользователя, ошибок Access Denied, удаления задачи Task Scheduler, повреждённого SMB отчёта и обрыва в состоянии \`Attempting\`.

**Ограничение:** CI подтверждает сборку .NET/PowerShell и офлайн-тесты. Установка Scheduled Task, сетевые права и фактическое отображение картинки на экране требуют испытания в реальном Windows-домене. Не включай массовый рабочий Repair до проверки.
