# Computer & Group Assignment — 0.4.0-preview.15

Открывается из **AD / GPO Deploy → GPO Operations → Computer & Group Assignment**.

Работает только с **текущим выбранным AD-доменом, OU и группой
Security Filtering**, которые были проверены в мастере. Группы не
создаются, GPO не переименовываются/не перепривязываются.

## Как добавить компьютер

1. Выбери компанию и выполни **Connect / Refresh** в AD/GPO Deploy.
2. В GPO Operations открой **Computer & Group Assignment**.
3. Введи имя ПК или оставь поиск пустым (до 150 записей из OU),
   нажми **Find computers**.
4. Проверь колонку Group membership: **Direct** (прямое членство),
   **Nested** (членство через другую группу), **Primary** (основная AD-группа компьютера), **None**.
5. Выдели ПК, выбери **Add to group** или **Remove from group**.
6. Нажми **Preview membership change**. Менеджер проверит
   принадлежность компьютера к выбранной OU, AD GUID компьютера
   и группы, текущие права и состояние членства.
7. Нажми **Apply group change** и введи точный
   **sAMAccountName компьютера с символом $ в конце**.
   Это отдельное подтверждение записи в Active Directory.
8. После проверки результата нажми **Refresh membership**.

**Remove** удаляет только прямое членство. Если компьютер действует
на основании вложенной группы, операция не удаляет вложенные
права автоматически — нужно проверить структуру AD вручную.
**Add** не выполняется, если компьютер уже имеет действующее членство.

## Безопасность и ограничения

- Сканирование и Preview — **read-only**; изменяет AD только Apply.
- План Preview действителен **5 минут**. Перед Apply заново проверяются
  выбранная OU, AD-объекты, GUID, USN группы и статус членства.
- Нужен writable DC и достаточные права администратора
  на изменение member у выбранной security group.
- Критические и привилегированные группы исключены.
- Используется встроенный модуль Windows PowerShell 5.1 с LDAP
  Signing + Sealing через текущую/явно введённую сессионную учётную
  запись. Отдельной установки PowerShell-скрипта и RSAT нет.
- Одна подтверждённая операция обрабатывает один компьютер;
  неконтролируемой массовой записи не происходит.
- Добавление в группу не запускает RPC, не меняет GPO Link и не
  гарантирует мгновенного применения политики. Для обновления
  токена безопасности компьютера может потребоваться его перезагрузка,
  после чего Client Health поможет проверить статус кампании.

GitHub Actions выполняет offline проверки синтаксиса/защиты,
но **реальная запись AD не выполняется в CI**. Сначала проверить
в тестовом домене и OU с выделенной группой без административных
привилегий. Лишь затем переходить к production.


## Защитные проверки preview.14

Перед изменением проверяется действительное числовое значение `uSNChanged` AD-группы, в том числе если ADSI возвращает составной 64-битный тип. Непроверяемый USN блокирует запись. Дополнительно проверяется SID группы: встроенные и стандартные доменные группы с низкими RID запрещены даже после переименования. Если RootDSE не подтверждает writable DC, Apply недоступен. Непосредственно перед изменением заново проверяются DN, GUID и SAM компьютера. Эти проверки *не заменяют* тестирование в отдельной AD OU с непривилегированной security group.

## Защита primary group в preview.15

Система отдельно проверяет `primaryGroupID` выбранного компьютерного объекта и RID из SID целевой security group. Если они совпадают, в списке отображается **Primary** и операции прямого Add/Remove блокируются. Primary group не всегда отражается в `memberOf`, поэтому прежнее отображение `None` в таком случае было бы неверным. Проверка выполняется снова при Preview/Apply. Для изменения первичной группы нужно использовать штатное администрирование AD, а не этот интерфейс. Для остальных изменений предварительный план также привязан к `primaryGroupID`, и прямо перед записью это значение перечитывается; любое изменение блокирует Apply.
