# UniversalDiagnostics в LockScreen Campaign Manager

Реализация: встроенный C# порт канонического
\`sgennadi/UniversalDiagnocticsModule/embedded/dotnet/UniversalDiagnosticsEmbedded.vb\`.
Контракт: \`universal-diagnostics/v1\`.

**Нет второго EXE, GitHub-токена, сетевых запросов или сбора диагностики
в фоне.** Записи делаются только после нажатия «Сохранить локально» в окне
ошибки. Доступ к сети открывается только по отдельному действию пользователя
«Создать GitHub Issue», при котором приложение копирует текст в Clipboard,
а Issue открывается **пустым** в браузере. Пользователь должен сам
просмотреть, вставить и отправить текст.

Локальная очередь:
\`%LOCALAPPDATA%\UniversalDiagnostics\<sha256(project)[0:16]>\<uuid>.json\`.

Пример полей:
- \`event.schema\`, \`event.id\`, \`timestamp_utc\`;
- \`project\`, \`component\`, \`error_type\`, \`code\`, \`level\`;
- \`version\`, \`summary\`, \`platform\`, \`architecture\`, \`fingerprint\`;
- \`delivery.status=pending\`, \`delivery.url=""\`.

Перед записью выполняется очистка IP, email, SID, GUID, UNC-путей,
пути к локальным файлам, учётных записей, доменов, BitLocker-ключей и
строк с признаками секретов. Это **не гарантия** удаления всех возможных
частных данных: оператор обязан проверить preview перед публикацией.

Локальный журнал \`%LOCALAPPDATA%\LockScreenCampaignManager\errors.log\`
сохраняет только очищенный тип ошибки, HResult, компонент и короткий текст.
Логи предыдущих версий автоматически не удаляются.

Self-test проверяет алгоритм редактирования, формат JSON, fingerprint,
статус \`pending\` и сохранение очереди во временный тестовый каталог.
Ручная отправка в GitHub Issues не является подтверждением доставки
до нажатия Submit и появления Issues в GitHub.

## Интеграция rc.2 — сохранение ровно проверенного отчёта

Встроенный C# адаптер использует контракт universal-diagnostics/v1 и текущую
версию сборки менеджера. После проверки администратором сохраняется именно
отображённый JSON, включая тот же UUID/UTC. Подмена fingerprint, версии,
имени проекта, структуры или статуса доставки блокируется.
Добавлено скрытие MAC-адресов. Отправка данных в GitHub отсутствует:
кнопка GitHub Issue открывает ручную форму и копирует preview в Clipboard;
отчёты pending не считаются доставленными.


## Local Error Trends (0.4.0-preview.8)

Через **Diagnostics → Error trends** можно проанализировать до 250
сохранённых UniversalDiagnostics v1 отчётов: количество повторений
одного fingerprint, компонент, тип ошибки, HResult, уровень, первое
и последнее время, последнюю версию приложения. Анализ работает
**только локально**, без сети и фоновых запусков.

Файлы \`*.json\` сначала проходят проверку схемы, ID и имени файла,
срока, проекта, полей, fingerprint и очистки потенциально конфиденциальных
данных. Повреждённые файлы или вручную переименованные отчёты
не попадают в статистику; счётчик **Rejected / invalid** виден отдельно.
Это не статистика всех ошибок Windows: учитываются только отчёты,
которые администратор сам сохранил ранее.

Кнопка **Export aggregate JSON** доступна только после анализа.
В отчёт не входят исходные тексты исключений, UNC/локальные пути,
имена компьютеров, UUID отдельных событий или полные логи.
Отправка в GitHub Issues остаётся отдельным **ручным** действием
пользователя после самостоятельной проверки. Ни один файл не
отправляется автоматически.

До полной удалённой доставки необходимо безопасное управление
GitHub credentials и отдельное согласие на публикацию конкретного
уже очищенного отчёта. В версии 0.4.0-preview.8 этого нет.


## GitHub Actions: автоматический анализ уже опубликованных Issues

Workflow **Review published diagnostic Issues** находится в
\`.github/workflows/diagnostics-review.yml\`. Он запускается
ежедневно (03:17 UTC), по событию открытия/изменения Issue,
а также вручную через **Actions → Review published diagnostic Issues
→ Run workflow**.

Workflow использует **только встроенный краткоживущий GITHUB_TOKEN**
с минимальными правами \`contents: read\`, \`issues: read\`.
Просматриваются не более 1000 Issues в закреплённом приватном
\`sgennadi/LockScreenCampaignManager\`. Скрипт принимает
только ранее опубликованный администратором JSON с корректной
схемой universal-diagnostics/v1, project, event ID, SHA-256
fingerprint, версией, временем и допустимыми категориями. Обычные
Issues и Pull Requests пропускаются.

Результат — сводка GitHub Actions и JSON-артефакт
**LSCM-Diagnostics-Review**: количество повторов и список номеров
Issues по fingerprint. Тело Issue, исходные исключения, имена
компьютеров, IP, UNC-пути, пароли и токены в артефакт **не копируются**.
Никакие Issues автоматически не создаются, не редактируются и не закрываются.

**Важно:** workflow не собирает данные с компьютеров и **не отправляет
локальные отчёты автоматически**. Сначала администратор сам изучает
очищенный report и публикует его через \`GitHub Issue\` в GUI.
Только после публикации Issue попадает в регулярный анализ.
Если GitHub API недоступен или разрешения недостаточны, workflow
завершается ошибкой вместо того, чтобы выдать ложный «0 проблем».

\`tools/test_diagnostics_issue_review.py\` проверяет парсер на
подменённых fingerprint, дубликатах, неверном repository и приватных
данных. Этот offline тест выполняется перед Windows x86/x64 сборками.


## Автоматическое подтверждение workflow (preview.10)

Workflow `Review published diagnostic Issues` дополнительно запускается при изменении трёх его файлов в `main` (`diagnostics-review.yml`, `diagnostics_issue_review.py`, `test_diagnostics_issue_review.py`). Это позволяет проверить GitHub Actions до первого ежедневного запуска. Остаются ранее включённые `workflow_dispatch`, расписание и события Issues. Выполнение только читает уже опубликованные вручную Issues и сохраняет агрегатный JSON. Отправки локальных логов, записи в Issues, повышения прав или RPC нет.
