# gMSA Unattended Repair — настройка и проверка (0.4.0-preview.8)

## Просмотр очереди после Disable

Вкладка **GPO Operations → gMSA 24/7** теперь сохраняет список ожидающих
Repair даже при отключённой задаче gMSA. Открой менеджер **на том же
Windows-сервере с повышенными правами**, выбери тот же домен, OU и
Security Group. В таблице остаются компьютеры и статусы `Queued`,
`AwaitingTask`, `AwaitingHealth`, `Attempting`, `NeedsAttention`.
Нижняя строка показывает количество записей каждого типа.

**DISABLED — queue inspection only:** это исключительно проверка.
`Cancel selected` и отправка новых Repair отключены. Проверка не
запускает RPC, не изменяет очередь, не меняет дату одобрения и не создаёт
новые задачи Task Scheduler. Состояние `Attempting` будет безопасно
восстановлено в `AwaitingTask` только в следующем настоящем цикле
запущенного worker, после повторного включения. `Queued` продолжат
обрабатываться **по прежним правам**, в пределах 14 дней/20 попыток.
Неверная OU/группа или отсутствие прав локального администратора блокируют
просмотр защищённой очереди.

Для повторного включения используй **Configure gMSA → Install / Repair**,
после чего проверь **Check**, **Run gMSA test** и свежий heartbeat.
Даже наличие heartbeat не означает, что клиент успешно применил изображение.


Отдельная задача Windows Task Scheduler под управляемой сервисной учётной
записью gMSA работает даже после полного выхода администратора из Windows.
Пароль не сохраняется ни в программе, ни в файлах: Windows и AD управляют им.
Задача должна работать на постоянно включённом доменном Windows-хосте,
желательно выделенном member server, а не контроллере домена.

**Важно:** одна установка поддерживает одну пару OU + Security Group и один
домен. Административный GUI запускается на ТОМ ЖЕ Windows-хосте с повышенными
правами для записи в защищённую системную очередь. RSAT не требуется ни GUI,
ни рабочему процессу; создание gMSA выполняется на DC стандартными AD cmdlets.

## 1. Создать gMSA в AD (на контроллере домена)

Пример для example.com; замени на собственные имена.

    Import-Module ActiveDirectory
    Get-KdsRootKey

Если ключа нет:

    Add-KdsRootKey -EffectiveImmediately

В production следует дождаться готовности и репликации KDS (до 10 часов);
не использовать backdated KDS root key ради сокращения ожидания.

Разрешить получать gMSA пароль только одному управляющему серверу:

    New-ADGroup -Name 'LSCM-gMSA-Hosts' -GroupScope Global -GroupCategory Security
    Add-ADGroupMember -Identity 'LSCM-gMSA-Hosts' -Members 'LSCM-SRV01$'
    New-ADServiceAccount -Name 'gmsaLSCM' -DNSHostName 'gmsaLSCM.example.com' -PrincipalsAllowedToRetrieveManagedPassword 'LSCM-gMSA-Hosts' -KerberosEncryptionType AES128,AES256

Если группа уже существует, проверь её вместо повторного создания. После
включения сервера в группу может потребоваться обновление Kerberos tickets
компьютерной записи или перезагрузка сервера.

На управляющем сервере проверить учётную запись (AD PowerShell module нужен
только для этой первоначальной подготовки, не для приложения):

    Install-ADServiceAccount -Identity 'gmsaLSCM'
    Test-ADServiceAccount -Identity 'gmsaLSCM'

Результат Test-ADServiceAccount должен быть True.

## 2. Минимальные права

- Дать gMSA право Log on as a batch job (SeBatchLogonRight) на управляющем
  Windows-сервере через отдельную ограниченную GPO.
- Дать gMSA чтение выбранных AD/GPO/SYSVOL и SMB каталога обратной связи.
- Дать право администратора только на ОДОБРЕННЫХ целевых ПК, чтобы Task
  Scheduler RPC мог создавать SYSTEM задачу. Не добавлять gMSA в Domain Admins,
  Enterprise Admins и локальные администраторы управляющего сервера.
- Клиентам разрешить собственные отчёты в отдельной защищённой SMB-шаре;
  запретить обычным пользователям перезаписывать чужие отчёты.
- Не отключать антивирус, UAC, Windows Firewall и аудит ради RPC.

Security Group будут автоматически заполнены из текущей конфигурации менеджера.
Нажми **Проверить**, затем **Установить / Repair** и подтверди действие.
Это полностью нативная установка через Windows API, без PowerShell-скрипта.

Установщик проверяет SID учётной записи, принадлежность хоста домену,
создаёт каталог в ProgramData, копирует EXE в защищённую папку bin и
регистрирует задачу LSCM-Gmsa-UnattendedRepair.

ACL конфигурации и EXE: запись только SYSTEM и Administrators, gMSA имеет
только чтение. ACL очереди/статуса: SYSTEM и Administrators имеют полный
доступ, gMSA — Modify. Обычные пользователи не получают прав записи.

Task Scheduler запускает тот же EXE каждые две минуты с параметром
--gmsa-repair-once. Тип входа — Password (Windows получает managed password
от AD, никакой пароль в параметрах установки не передаётся). S4U не
используется, поскольку ему недоступна сеть.

## 4. Управление в GUI

Открой менеджер на том же Windows-хосте, выбери домен, DC, OU и Security
Group. Затем GPO Operations → gMSA 24/7.

Если задача установлена и работает от ожидаемой учётной записи, доступен
переключатель «24/7 gMSA — отправлять НОВЫЕ подтверждённые Repair».

Выбери 1–25 компьютеров в Client Health / Live или Push Now → Repair.
После Preview введи полный GUID GPO. Только после этого результаты
помещаются в защищённую машинную очередь.

Фоновый gMSA процесс перепроверяет AD OU, вложенную Security Group,
GPO, CampaignID и новый хеш плана перед новым RPC. Он сначала читает
свежий SMB-отчёт: если клиент сам исправился после включения, RPC не нужен.

Queued — одобренный, временно недоступный ПК;
Attempting — зафиксирована попытка RPC;
AwaitingHealth — Task Scheduler завершил задание, ждём подтверждение агента;
AwaitingTask — результат удалённого задания неизвестен, повтор запрещён;
NeedsAttention — ошибка или срок полномочий истёк, нужен администратор.

Лимиты: 20 попыток / 14 дней от исходного подтверждения,
не более одного RPC за цикл, до 20 SMB-проверок за цикл.
Старые пользовательские заявки не мигрируются автоматически.

## Проверка состояния Worker без отправки Repair

В **GPO Operations → gMSA 24/7** статус Task Scheduler и реальный heartbeat
показываются отдельно. Наличие задачи не гарантирует, что Windows смогла войти
под gMSA: нужен хотя бы один успешно запущенный рабочий цикл.

Через **Configure gMSA → Check** менеджер показывает сведения Task Scheduler,
последний код выполнения, время последнего и следующего запуска и метку
`Worker health`. Интерпретация:
- `Not verified` — от установленной задачи ещё не было сообщения worker;
- `Heartbeat received` — процесс запустился, но это НЕ подтверждение картинки;
- `Overdue` — нет нового heartbeat более восьми минут при настроенном интервале в две минуты;
- `Needs attention` — рабочий цикл сталкивается с ошибкой или недоступной SMB-шарой;
- `Not enabled` — выполнение отключено.

После **Disable** имя gMSA и путь SMB сохраняются и повторно подставляются
в мастере. Повторное **Install / Repair** не продлевает первоначально выданные
разрешения на Deferred Repair. Изменение OU/группы/учётной записи требует
отдельной проверки и разбора старых заявок. Проверка **Check** не запускает RPC.

## Дополнительная защита перед gMSA RPC (0.4.0-preview.8)

Даже если очередная машина не вошла в первые 20 отчётов текущего цикла,
worker **повторно считывает её персональный Client Health непосредственно
перед удалённым Repair**. Если есть подтверждённый свежий Healthy-отчёт,
заявка закрывается без RPC. Если JSON повреждён или не соответствует
ожидаемому формату, заявка переводится в `NeedsAttention` и не запускается
автоматически. При отказе в доступе или ошибке чтения SMB весь текущий
цикл откладывает удалённые задания, сохраняя исходное разрешение.

Проверка не выполняет повторную регистрацию задачи при неизвестном результате
предыдущей попытки. Отсутствие отчёта само по себе не означает, что компьютер
исправен или что задача уже выполнена.

## Проверка запуска под gMSA без Repair (новая кнопка в 0.4.0-preview.8)

После настройки на том же Windows-хосте открой **GPO Operations →
gMSA 24/7 → Configure gMSA** и нажми **Run gMSA test**.

Программа создаёт отдельную задачу `LSCM-Gmsa-ReadOnlyDiagnostic` без
триггеров (только ручной запуск) под той же gMSA. Она запускает тот же
защищённый EXE с аргументом `--gmsa-diagnose-once` и проверяет:

- выполняется ли процесс под SID нужной gMSA;
- не повреждены ли права NTFS на конфигурацию и исполняемый файл;
- доступна ли защищённая системная очередь в режиме чтения;
- разрешается ли DNS-имя домена;
- доступен ли SYSVOL для чтения под этой gMSA;
- доступна ли отдельная SMB-шара Client Health для чтения.

Результаты сохраняются локально в `ProgramData\LockScreenCampaignManager\GmsaWorker\status\diagnostic.json`.
Кнопка **Check** показывает последний отчёт. Если результат не появился,
проверь Last Task Scheduler result — регистрация задачи ещё не означает
успешного входа gMSA.

**Безопасность:** диагностическая задача не имеет расписания, не создаёт
новые GPO, не выполняет RPC, не меняет очередь и не запускает Repair на
клиентских компьютерах. Эта проверка не доказывает, что гMSA имеет права
администратора на удалённых ПК: это проверяется отдельно на тестовой OU.
При Disable / Remove Task отключаются или удаляются обе задачи.

## Проверка актуальности результатов Run gMSA test

Новый диагностический отчёт привязан к SID gMSA, домену, OU, Security Group,
SMB-шаре Client Health и пути установленного EXE. Менеджер не принимает
предыдущий успешный результат после изменения этих параметров.
Отчёты старше одного часа отображаются как устаревшие с предложением
повторить `Run gMSA test`. Старый формат отчёта без отпечатка области
действия не считается подтверждением.

Это проверка доступа под gMSA, но НЕ доказательство успешной смены
Lock Screen на клиентских компьютерах. Для этого нужны Client Health
и контрольная проверка тестового компьютера.

## Восстановление после перезагрузки управляющего сервера (0.4.0-preview.8)

Обновлённая нативная установка создаёт два триггера в **той же**
`LSCM-Gmsa-UnattendedRepair` задаче Task Scheduler: каждый день с повторением
раз в две минуты и отдельный **At system startup + 3 минуты**. Если сеть или
контроллер домена ещё недоступны, регулярная задача попробует следующий
запланированный цикл. Параллельный запуск двух экземпляров по-прежнему
отключён (`IgnoreNew`), повторная попытка RPC за один цикл ограничена.

**После обновления EXE нужно один раз открыть Configure gMSA и нажать
Install / Repair**, чтобы обновить расписание существующей задачи.
Новая проверка Scheduler не считает устаревшую однотриггерную задачу готовой;
очередь и старые подтверждения администратора при переустановке сохраняются.

Если Windows выключилась при регистрации RPC:
- `Attempting` → `AwaitingTask` в новом цикле без повторной отправки задания;
- `Queued` остаётся очередью и может выполниться только в пределах прежнего
  утверждённого окна;
- `AwaitingHealth` и `AwaitingTask` продолжают только проверять новый Client Health;
- по истечении двух часов без нужного отчёта запись переходит в
  `NeedsAttention` — автоматический RPC запрещён.

Вкладка gMSA показывает число распознанных прерванных попыток в сводке
последнего цикла, но это **не** подтверждение успешного выполнения на клиенте.

Приёмочное испытание на настоящем AD: подтвердить `Run gMSA test`,
запустить Repair на тестовой OU, перезагрузить сервер после помещения заявки
в очередь и проверить, что задача стартовала после включения, а неизвестный
результат RPC не приводит к повтору. CI воспроизводит модель остановки
процесса, но не может перезагрузить твой Windows-хост или войти под gMSA.


## Мониторинг gMSA Queue Health в GUI (0.4.0-preview.8)

Вкладка **GPO Operations → gMSA 24/7** теперь дополнительно показывает
колонку **Health** и поле **Filter**: All, Needs review, Monitoring,
Queued, AwaitingTask, AwaitingHealth, Attempting. Строки, требующие
внимания администратора, расположены первыми. В строке состояния
показывается число ожидающих записей, ошибок и элементов для проверки.

**Auto-refresh (30 s)** обновляет список автоматически, пока открыта
вкладка. Чтение защищённой очереди выполняется в отдельном потоке GUI,
без зависания окна в ожидании файловой блокировки. При закрытии вкладки
автоматическое обновление прекращается.

Предупреждения: **Approval expired** — прошло 14 дней;
**Retry limit reached** — 20 попыток; **Retry delayed** — запланированная
повторная попытка задерживается; **RPC unconfirmed** — запись `Attempting`
старше 15 минут или gMSA остановлен; **Health confirmation overdue** —
нет подтверждения Client Health в течение 2 часов. Эти значения лишь
помогают диагностике: не означают новую попытку RPC, не изменяют статус
в очереди и не подтверждают успешное применение изображения.

Для `AwaitingTask` автоматический повтор RPC по-прежнему **запрещён**,
даже если компьютер снова появился в сети. Для `Queued` действуют
исходные сроки одобрения. При `Disabled` очереди доступны только для
просмотра администратором. Отчёты UniversalDiagnostics могут быть
сохранены локально после просмотра, но не отправляются на GitHub сами.
