# Production Readiness и Device Repair Evidence

Версия приложения **0.4.0-preview.8**, не повышается. GUI на английском.
Встроенный C# код, без отдельных *.ps1-установщиков или RSAT.

## Production Readiness

В менеджере на выделенном доменном Windows-сервере запусти приложение
с правами локального администратора, выбери правильные **Domain / OU /
Security Group** и открой **GPO Operations → gMSA 24/7 → Production Readiness**
(или **Configure gMSA → Readiness**).

На экране 11 проверок:
1. Защищённая конфигурация работника существует и читается.
2. Домен, OU и группа совпадают с установленной конфигурацией.
3. gMSA Worker явно включён.
4. Нативная задача Task Scheduler соответствует SID/EXE,
   двухминутному циклу и запуску после загрузки.
5. Встроенная проверка Netlogon видит установленный gMSA.
6. Heartbeat свежий и относится к текущей конфигурации.
7. Read-only gMSA Diagnostic Test выполнен под gMSA недавно и успешно
   проверил SYSVOL и Client Health SMB.
8. Администратор может прочитать каталог SMB обратной связи.
9. Защищённая очередь читается и проходит валидацию.
10. Нет незавершённых RPC с неизвестным исходом.
11. Нет записей, требующих ручного расследования.

Красный **Blocked** означает, что пилот пока нельзя считать готовым.
Жёлтый **Warning** означает, что существуют элементы для ручной проверки.
Зелёный **Pass** означает только успешную локальную проверку.
**READY FOR PILOT не означает production-ready / весь AD успешно обработан.**
Открытие отчёта не изменяет GPO, Task Scheduler или Client Health и
не выполняет RPC. Кнопка **Export safe JSON** доступна после проверки
и сохраняет отчёт только по выбору администратора. В отчёт не входят
реальные OU, SID, UNC-пути, имена серверов, компьютеров или пароли.

## Порядок приёмки на тестовой OU (только вручную)

1. Проверь права выделенного gMSA в AD и доступ к SYSVOL/SMB;
   выполни в Configure gMSA **Install / Repair → Check → Run gMSA test**.
2. Открой Production Readiness и убедись, что нет Blocked.
3. Создай кампанию на ограниченной тестовой OU и группе компьютеров.
   Проверь SYSVOL, GPO и реестр на тестовом Windows 11.
4. На клиенте отдельно подтвердите реальное изображение Lock Screen;
   здоровый SMB-отчёт сам по себе недостаточен.
5. Вызови Repair Selected с Preview и полным GUID для тестового
   отключённого компьютера; проверь появление **Queued**.
6. Перезагрузи управляющий сервер с gMSA, не открывай GUI.
   Проверь, что Task Scheduler продолжил циклы после загрузки.
7. При имитации остановки Worker после **Attempting** убедись,
   что запись перешла в **AwaitingTask** без повторного RPC;
   сверь Task Scheduler на клиенте.
8. Проверь нормальное подтверждение через Client Health и сценарий
   отсутствия отчёта 2 часа → NeedsAttention. Не запускай
   повторный RPC без нового одобрения.
9. Повтори проверку при **Disable** и **Remove task**, затем
   **Install / Repair** с неизменёнными правами очереди.

Пока испытания на настоящем AD/gMSA не выполнены, не выдавай
приложение за production-verified и не публикуй stable автоматически.

## Device Repair Evidence

В **GPO Operations → Device & Repair Dashboard**, загрузи
**Load verified AD devices**, **Refresh reports**, выдели один компьютер.

**Device Details** показывает последнюю сохранённую очередь Repair:
User или gMSA, текущий статус, дату исходного одобрения,
рассчитанный срок действия (14 дней), количество попыток (лимит 20),
время последней попытки, время отправки RPC, следующую проверку
и последнюю сохранённую причину ожидания.

Это **не полный журнал каждого RPC**, так как нынешняя очередь хранит
лишь последнее состояние. Локальная история Client Health содержит
ранее сохранённые **Snapshot / Final**, но не гарантирует показ
картинки на экране. При AwaitingTask / AwaitingHealth / Attempting
повторный RPC запрещён до расследования.
